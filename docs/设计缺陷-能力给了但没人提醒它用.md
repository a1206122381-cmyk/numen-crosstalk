# 设计缺陷：能力给了，但没有任何东西提醒它去用

---

## 一、你指出的问题

> 每次都要我手动让她们听和说，否则就想不起来要听。
> **这对大型长程协作任务来说是致命的。**

**这是对的，而且是我设计上的疏漏。**

我上一轮把架构从「推」改成「拉」，理由是拉模型不占主人窗口、不形成寒暄循环。
**但"拉"要成立，前提是它得知道有东西可拉。**

原来只有 `hear` 工具，而**没有任何东西提醒它去调**。
实测结果就是：旁边刚有人跟它说过话，它一无所知。

---

## 二、缺的那一环：`EventQueue`

我查 Numen 源码时漏掉了一个关键机制。它的 `EntityAgentLoop` 里有一个
**持久化的事件队列**，会「攒着」消息，然后按规则**自动送进上下文**：

```java
// EntityAgentLoop.maybeDrain() —— 在 6 处被调用（tick 心跳、回合结束…）
  → EventQueue.shouldDrain(now, level)
       有 urgent 的          → 立刻排空
       条数 ≥ 门槛           → 排空
       最老的等了够久        → 排空
```

**这正是缺的那一环**：消息可以"躺在它的收件箱里"，到点自己进去。

而且它的设计文档里写得很清楚：

> **正确性从不依赖叫醒**：`hasUrgent` / `shouldDrain` 是随时可问、答案一致的状态；
> 丢一次叫醒，消费者按自己的节律（内脑的 tick 心跳）一问就发现。

## 三、所以现在的投递分两档

| 情况 | 做法 | 效果 |
|---|---|---|
| **普通发言** | 推进事件队列，**不标 urgent** | **不打断它手头的事**，但下次开轮 / 攒够了自然就看得到 |
| **紧急发言** | 标 `urgent=true` | 立刻把它叫起来 |

**"急不急"由说话的人自己判断**（`say(text, urgent=true)`），我们不替它定义。

### 关键差别

```
之前：AAA 说完 → Dva 必须被主人提醒才会 hear → 才知道有人在跟它说话
现在：AAA 说完 → 消息进了 Dva 的队列 → Dva 下次开轮自然看到
```

**「听」从"要记得做的事"变成"会自己到的东西"。**

## 四、顺带修了一个名单准确性问题

我发现 `AgentLoopRegistry` 有个比 `CompanionHome.known()` 更好的方法：

| 方法 | 含义 |
|---|---|
| `CompanionHome.known()` | **磁盘目录**里存在过哪些同伴——含休眠的 |
| **`AgentLoopRegistry.loadedEntityUuids()`** | **真正已加载（在世界里）**的同伴 |

投递当然只该投给在场的，所以改用了后者。

---

## 五、`say` 的工具说明也跟着改了

**之前**：
> Say something out loud, so that anyone here can hear it. Use it when you
> actually want to be heard...

**现在**：
> Say something out loud, so that anyone here can hear it. **They will come
> across it on their own — normally without being interrupted, unless you mark
> it urgent.** Use it when you actually want to be heard, not for thinking out loud。

**为什么改**：说明里不说清楚"对方会自己看到"，同伴可能会以为必须等对方主动来听，
于是自己也不主动说。**工具的说明会影响它怎么用这个工具。**

---

## 六、设计原则小结（供开源文档用）

这三层是配套的，缺一个都不成立：

| 层 | 作用 | 缺了会怎样 |
|---|---|---|
| **事件队列投递** | 让消息**自己到达** | 它想不起来去听（← 你发现的问题） |
| **`hear` 工具** | 让它**主动查**完整未读 | 只能被动接收，错过的不补 |
| **`say(urgent)`** | 紧急时**打断** | 急事也要等到下次开轮 |
