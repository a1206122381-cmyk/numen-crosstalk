## 二、speech-mcp 重构结果

### 2.1 去掉了硬编码

原来写死了 `D:/Minecraft/AI社会实验版-server/...`。现在三级优先级：

```
命令行参数 > 环境变量 > 默认值
```

```bash
node index.mjs --port 9101 --speaker Lin \
  --out <存档>/numenresident/speech.jsonl \
  --heard <存档>/numenresident/heard.jsonl
```

### 2.2 支持多同伴共用一个实例

新增 `as` 参数（自报名字）。这样不必每只同伴起一个进程：

| 部署方式 | 身份来源 |
|---|---|
| 每只一个实例 | `--speaker` 固定（最准，推荐） |
| 多只共用一个实例 | 调用时带 `as` |

**游标按个体分开记**，所以共用实例时各自的"未读"互不影响。

### 2.3 集成测试：14/14 通过

```
✅ 暴露 hear/say/who_is_here
✅ 说明里没有"你应该/必须"类祈使句    ← 措辞纪律有测试保障
```

## 三、重大发现：记忆系统已有一半

`numen-orchestrator` 里已经有 `Memory.java`（7.2 KB），**而且设计是对的**：

```java
Memory.recall(name)                   // 取记忆
Memory.remember(name, summary)        // 存记忆
Memory.summarizeFromChat(uuid, 600)   // 从对话抽摘要
Memory.bindPath(path)
```

**关键：它按名字存，不按 UUID。**

它的注释已经预见了我们踩的坑：

> 记忆按 UUID 存就等于"每次重生都失忆"——实测踩过这个坑

**而且已经接进 Orchestrator 了**（4 处调用：绑定路径、抽摘要、比对、取回）。

### 3.1 ⚠️ 但有个关键细节

**它抽摘要的「来源」仍然是 UUID 绑定的 `chat.jsonl`。**

```
Memory（按名字）  ← 摘要在重启后能延续  ✅
       ↑
chat.jsonl（按 UUID）  ← 重启后旧文件被删  ❌
```

**所以现状是**：
- 摘要在重启后**能**延续（按名字）
- **但摘要的来源在重启时会被删** → 必须在**销毁前**抽取

**这引出下一步的关键点**：抽取时机。

## 四、顺带确认：token 余量比想象的大

```
模型窗口            64000
auto-compact 阈值   51000
实测单次输入         16959 ~ 20471
→ 距阈值还有 30529 tokens 余量
```

**所以"上下文会爆"短期不会发生。** 真正该优化的是**回合频率**，
而不是加记忆层——这一点再次印证拉模型的正确性。

## 六、待确认的设计点

### 6.1 队列文件放哪

| 方案 | 优点 | 缺点 |
|---|---|---|
| 服务端存档内（现在这样） | 客户端/服务端都能读写 | 依赖服务端路径 |
| 独立数据目录 | 干净、与存档解耦 | 需要额外配置 |

**我倾向保留在存档内**——它天然跟着世界走，换存档就换队列，符合直觉。

### 6.2 `seq` 由谁分配

| 方案 | 优点 | 缺点 |
|---|---|---|
| **写入方（子mod）分配** | 严格递增，不受文件操作影响 | 需要跨进程原子性 |
| 读取方（MCP）按数组下标补 | 简单 | 文件重写会错位 |

**已实现的做法**：写入方写 `seq`，没有则读取方按数组下标兜底。
**建议子mod 写的时候就带上 `seq`**（用一个内存计数器 + 启动时扫最大值）。
