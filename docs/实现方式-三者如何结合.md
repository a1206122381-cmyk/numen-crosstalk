# 实现方式：三者结合，但靠「文件」**完全**解耦

---

## 一句话回答

**是三者结合，但真正的设计是「mod 和 MCP 之间零调用」——它们只通过两个文件通信。**

这一点比听起来更彻底。我做了严格验证（排除注释行后检查真实代码）：

| 检查 | 结果 |
|---|---|
| `ClientChatRelay` 是否调 Numen API？ | ✅ **零调用**。只用 Minecraft 原版 API + `java.nio` 写文件 |
| `speech-mcp` 是否知道 Minecraft？ | ✅ **零概念**。只用 node 内置模块（`http`/`fs`/`path`） |
| mod 是否知道 MCP 存在？ | ✅ **不知道**。相关字样只出现在注释里 |

**这意味着两边可以各自替换**：换个 MCP 实现、换个 mod、
甚至用别的语言写个程序对接同一个文件，都能工作。

---

## 一、三个部分各是什么

| # | 部分 | 类型 | 装在哪 | 职责 |
|---|---|---|---|---|
| 1 | **`numen-orchestrator`** | Forge **mod** | 客户端 | 听聊天写队列；读发言流；唤醒；记忆 |
| 2 | **`numen-resident`** | Forge **mod** | 服务端 | 写身份名册（**可选**） |
| 3 | **`speech-mcp`** | **MCP 服务器** | 任意进程 | 给同伴 `hear` / `say` 两个工具 |

**不是"mod 群"**——两个 mod 完全独立，各装各的，只是恰好配套。

## 二、真实的 I/O 契约（从代码读出来的）

| 文件 | 谁写 | 谁读 |
|---|---|---|
| `heard.jsonl` | **mod**（`ClientChatRelay.enqueue`） | **MCP**（`hear()`） |
| `speech.jsonl` | **MCP**（`say()`）+ **mod**（`appendSpeech` 中继） | **mod**（`pushUrgentSpeech`） |
| `agents.json` | mod（`numen-resident`，可选） | MCP（`who_is_here()`） |
| `heard-cursor.json` | **MCP**（自己维护读取位置） | MCP |

**注意最后一行**：游标归 MCP 自己管，**mod 完全不知道它存在**。

```
                     heard.jsonl                speech.jsonl
                    （别人说了什么）             （同伴说了什么）
                          │                          │
        ┌─────────────────┼──────────────────────────┼─────────────────┐
        │                 │                          │                 │
   写 ──┤  mod 写          │                     读 ──┤  mod 读         │
        │  (ClientChatRelay)                         │  (pushUrgentSpeech)
        │                 │                          │                 │
   读 ──┤  MCP 读          │                     写 ──┤  MCP 写         │
        │  (hear)          │                          │  (say)          │
        └─────────────────┼──────────────────────────┼─────────────────┘
                          │                          │
                       同伴调 hear()            同伴调 say()
```

## 三、一次完整对话的实际路径

### 场景 A：Wei（同伴）说了一句，Lin（另一只同伴）应该能听到

```
① Wei 的大脑决定说话
   └─ 它调 MCP 工具 say("我去挖矿了")

② speech-mcp 收到调用
   └─ 追加一行到 speech.jsonl
      {"seq":..,"t":..,"name":"Wei","text":"我去挖矿了"}

③ mod 的 pushUrgentSpeech 轮询 speech.jsonl
   ├─ 发现新行
   └─ 检查 urgent 字段
      ├─ 无 urgent → **什么都不做**（躺着，等 Lin 自己来读）
      └─ urgent=true → 调 pushEvent 唤醒 Lin

④ Lin 在某一轮里决定调 hear()
   └─ speech-mcp 读 heard.jsonl
      ├─ 按 Lin 的游标过滤出未读的
      ├─ 过滤掉 Lin 自己说的
      └─ 返回 "[14:23] Wei: 我去挖矿了"
```

**关键在第 ③ 步**：普通消息**什么都不做**。
Wei 的话静静躺在文件里，直到 Lin 想看。

### 场景 B：一个普通玩家在聊天里说话

```
① 玩家打字 → 服务端广播 → 客户端收到聊天包
② ClientChatRelay.onChat 触发
   ├─ 解析 "<名字> 内容"
   ├─ 过滤：系统消息跳过 / 自己说的跳过
   └─ 追加一行到 heard.jsonl（带 seq）

③ 同伴调 hear() 时读到 —— 或者永远不读，随它
```

**注意 ②**：`ClientChatRelay` **只写文件，不调任何 Numen API**。
所以它不依赖 Numen、不依赖 Mindcraft，**谁在聊天它都记**。

## 四、为什么这样设计（三个理由）

### 理由 1：主人窗口零污染 ⭐

同伴的对话历史里**只有它自己调 `hear()` 拿到的内容**——
而且那是它**主动要的**，不是被塞进来的。

**别的 AI 说什么，永远不会出现在主人和助手的对话流里。**

### 理由 2：进程解耦

| 好处 | 说明 |
|---|---|
| MCP 不知道 Minecraft | 可以拿去给任何"多个 AI"的场景用 |
| mod 不知道 MCP | 换成别的 MCP 实现也能用 |
| 谁先启动都行 | 文件是共享状态，没有握手 |
| 崩一个不影响另一个 | 文件还在 |

**代价**：文件是唯一通道，所以有轮询延迟（mod 每 5 秒一轮）。

### 理由 3：可观测

```
<存档>\numenresident\
  heard.jsonl           ← 随时 tail，看同伴能听到什么
  speech.jsonl          ← 看它们说过什么
  heard-cursor.json     ← 看每个同伴读到哪了
```

**出问题不用猜**——直接看文件。这在调试阶段救过很多次。

## 五、哪些部分是必须的

| 部分 | 必须吗 | 不装的后果 |
|---|---|---|
| **`speech-mcp`** | ✅ **必须** | 同伴没有 `hear`/`say`，功能不存在 |
| **`numen-orchestrator`** | ⚠️ 取决于场景 | 没有"收聊天进队列"和"紧急唤醒"。**同伴之间仍可互相 `say`/`hear`**（它们自己读写 `speech.jsonl`） |
| **`numen-resident`** | ⬜ 可选 | `who_is_here()` 走降级路径 |

### ⭐ 最小可用组合：**只装 `speech-mcp`**

**它一个人就能让两个 AI 互相说话**——只要它们都读写同一个 `speech.jsonl`。

mod 的作用是**把"世界里的聊天"也接进管道**，
让不是 MCP 客户端的人（普通玩家、Mindcraft 这类外部 bot）也能被听见。

---

## 六、职责边界（一句话版）

| 部分 | 负责 |
|---|---|
| **mod** | 把**世界里的声音**接进管道，以及**紧急时唤醒** |
| **MCP** | 给同伴**一对耳朵和一张嘴**，并记住每个个体读到哪了 |
| **文件** | 两者的**唯一交界面**，也是唯一的共享状态 |

**mod 管「世界 ↔ 管道」，MCP 管「同伴 ↔ 管道」。它们从不直接说话。**
